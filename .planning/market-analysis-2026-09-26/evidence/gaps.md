## released-byo-e2e-job (confidence: high)

**Question:** On a fresh Ubuntu 24.04 host where sudo needs a password, prepared only with the released v1.3.3 install.sh asset, does the released v1.3.3 binary bring a runner online that completes a real job with gcc, docker and sudo apt steps? How long does the BYO first run take, and how many GB does it use, once setup_runner_image is included?

**Answer:** No. On a password-sudo Ubuntu 24.04 host prepared only with the released v1.3.3 install.sh, the released v1.3.3 binary never brings a runner online, so no job can run. The release is the same code as HEAD. The install.sh served at both /releases/download/v1.3.3/ and /releases/latest/download/ is byte-identical to the repo copy (sha256 8e5405…e4e9). The linux_amd64 binary reports go1.22.12, vcs.revision=64c30030 (HEAD), vcs.modified=false, and `--version` prints 1.3.3.

I ran the released binary against a systemd Ubuntu 24.04 container, using a local fake GitHub API and a local apt repo because the sandbox containers have no internet access. Preflight passed and fix_dependencies passed (about 29 s, +816 MiB). Then setup_runner_image failed on its first privileged line, `sudo mkdir -p /etc/apt/keyrings`, with "sudo: a terminal is required". The binary exited 4 (bootstrap_failed) after 39.7 s. The error names the failing step as "(unknown)". The runner user was never created and the runner was never registered.

I then tested each sudo command by actually running it as the SSH user (`sudo -n <path> --version`). Under the released sudoers, 9 commands that Apply/ApplyEphemeral use are refused: add-apt-repository, chmod, dpkg, gpg, ln, mkdir, tee, unzip and usermod. Two more that down/readback use are also refused: cat and cp. That makes 11 commands, 16 sudoers paths. The HEAD RenderSudoersEntry template covers all 21 commands. Because ephemeral mode's unit and finalizer scripts need `sudo tee` and `sudo chmod`, ephemeral BYO fails on every distro, not only Ubuntu. The requested `sudo -n -l` check is not usable here: it returned 0 for every path, because the user's %sudo rule allows everything with a password.

To measure a fixed path, I swapped in the HEAD sudoers and piped the rendered scripts over SSH in bootstrap order. Times below are install-only on a 4-vCPU sandbox with a local package repo:
- fix_dependencies: 29.3 s, +819 MiB.
- Measured image sections (Node, pip, Java, .NET, Docker, cmake): about 43 s, +1,315 MiB.
- create_runner_user: 0.4 s.
- download_runner: 6.1 s, +671 MiB unpacked runner plus the 215 MiB tarball cache.
- configure_runner: reached config.sh in 6.5 s, which then failed with 404 on the fake token as intended.

configure_runner downloads the 225 MB runner tarball a second time into the install directory (+215 MiB). Measured total disk is 3.16 GiB. Go, Chrome, Firefox and gh could not be fetched in the sandbox (egress blocked); estimating them plus the .debs apt-get keeps in its cache, a real fresh host needs about 4.5–5 GB and about 1.4 GB of downloads. Preflight only requires 2 GiB free. My projected first-run time with the image step included is about 3.5–5 min on a fast 4-vCPU host with ≥100 Mbps, and about 8–12 min on a 25 Mbps link or a 2-vCPU box. The old 110–149 s figure no longer applies.

After create_runner_user, `id runnerkit-runner` shows groups=992(runnerkit-runner) only, with no docker group. `usermod -aG docker` runs in setup_runner_image before the user exists and its error is suppressed (`|| true`). The Rust install silently skips for the same reason. The marker /var/lib/runnerkit/image-setup.json is written, so every later run prints "already complete, skipping" and the docker group is never added.

Simulating the job's steps as the runner user: gcc passes. `docker run hello-world` fails with "permission denied … /var/run/docker.sock". `sudo apt-get install -y jq` fails with "a password is required" unless install.sh was run with RUNNERKIT_GRANT_CI_SUDO=1, which the default one-liner does not do. Two controls confirm the fixes work: adding the CI sudoers makes the apt step pass, and adding the docker group after the user exists makes hello-world pass.

The Geckodriver and Go version lookups are fragile: a failed or rate-limited call to api.github.com or go.dev stops the whole bootstrap despite the intended fallback. I reproduced the Geckodriver case (rc=1). No real GitHub job was dispatched, because there are no credentials here and no user could supply a repo or PAT.

**Implication:** The code-stream conclusion is confirmed empirically on the released artifact. The strategy must start with a stabilization release (v1.3.4) before any growth work.

## runner-version-enforcement (confidence: medium)

**Question:** As of 2026-09-25, will a runner freshly bootstrapped at RunnerKit's hard pin (actions/runner 2.334.0, with upstream now at 2.337.0) register on a github.com personal-account repo and pick up jobs, persistent and --ephemeral alike, given GitHub's minimum-version enforcement and its 30-day update rule? And does the pinned-tarball model plus a 4-month release gap make RunnerKit non-functional without a release every 30 days or less?

**Answer:** YES, with medium confidence. A fresh RunnerKit install at 2.334.0 should still register on a github.com personal repo today and run jobs, both persistent and --ephemeral. This is inference: I did not run a live test because no throwaway repo or token was available. The reason it works is that RunnerKit never passes --disableupdate (script.go:56 and :109). GitHub's rule has two parts. First, a fixed registration ("Config") floor of 2.329.0, which 2.334.0 clears. Second, a 30-day update rule that controls job routing ("Runtime"). Discussion #194762 (2026-05-04) says runners with auto-update enabled "meet the 30-day requirement automatically, as long as they can reach the update service". FACT from the actions/runner source and GitHub docs: on github.com an outdated auto-updating runner gets a refresh message when a job is assigned (or within a week if idle), so the first job waits for the update. The runner then downloads the new version, checks its hash, and swaps symlinked bin and externals directories. It exits with code 3 (persistent) or 4 (ephemeral/--once), and run.sh / RunnerService relaunch it on the new version before it takes the job. RunnerKit meets both prerequisites: the ephemeral unit runs ExecStart=run.sh (script.go:185), and both paths chown the install dir to the service user (script.go:53 and :106), so the update can write there. Supporting evidence: issue #4421 (2026-05-14) shows an auto-updating svc.sh runner on Ubuntu 24.04 updating from 2.328.0 to 2.334.0. 2.328.0 is below the 2.329.0 floor, and the runner was updated rather than refused. Every 2026 report of "Runner version vX is deprecated and cannot receive messages" came from a pinned runner that does not update itself (mostly container, ARC or GKE images): #4203 (2.329.0, logs show disableUpdate=true), #4305 (2.330.0), #4392 (2.331.0), #4442 (2.332.0) and #4613 (2.336.0). So with --disableupdate, 2.334.0 would already be dead. The documented deadline was about 2026-07-08, 30 days after 2.335.0 shipped on 2026-06-08. The observed lag for 2.330.0 to 2.332.0 was about 63 to 66 days after the next release. #4613 reported 2.336.0 refused on 2026-08-06 while it was still the latest release; nobody explained that, and it is unresolved as far as I could read. Plans and dates: the discussion says "This change applies to github.com, including GitHub Enterprise Cloud and GitHub Enterprise Cloud with Data Residency". It lists only GHEC-DR (2026-07-31) and GHEC (2026-09-25, brownouts 2026-08-24 to 09-18), with no separate Free/Pro/Team row. I infer that personal accounts follow the github.com/GHEC date of 2026-09-25, and the runtime refusal of non-updating runners was already live on github.com in 2025. So the streams do not actually disagree: 2.329.0 is the registration floor, and the 30-day rule decides job routing. The pinned tarball and the 4-month gap since v1.3.3 (2026-05-19) therefore do NOT make RunnerKit non-functional, and no release every 30 days is needed. The costs are: every fresh install, and every ephemeral `up`, pays a full self-update before its first job; the runner breaks if the host cannot reach the update service or the #4421 bug leaves a 0-byte runsvc.sh (status 203/EXEC on the next restart); and it breaks the day GitHub raises the registration floor above 2.334.0, for which no date has been announced. Separately, doctor cannot see this: it compares the saved pin with the bundled pin (doctor.go:149), both 2.334.0, and never checks the version actually on disk or the latest upstream. Recommended model: resolve the latest actions/runner release when `up` runs. Take the per-asset SHA-256 from the "<!-- BEGIN SHA linux-x64 -->…<!-- END SHA linux-x64 -->" markers that every release body carries (for 2.337.0, linux-x64 is 70920811a4f8ad4328818682bca5c6469c1c942fab52448868071d0063816613) and verify it with sha256sum. Fall back to a bundled pin that a scheduled workflow bumps automatically, and keep auto-update enabled.

**Implication:** RunnerKit is not broken today because of the version pin, and a release every 30 days is not needed, as long as auto-update stays on. Treat "never pass --disableupdate" as a documented invariant: adding it would have killed 2.334.0 installs around July to August 2026. Recommended changes, in priority order:

1. Move to a resolve-latest installer. At `up` / `upgrade-runner` time, fetch the latest actions/runner release (github.com/actions/runner/releases/latest redirect or the API). Parse the SHA-256 between the <!-- BEGIN SHA linux-x64|linux-arm64 --> markers in the release body and check it with `sha256sum -c`. Keep the bundled pin only as an offline fallback that must be at least the registration floor (2.329.0 today). The pinned hash was copied from the same release body, so this gives up no real trust. Auto-bump the fallback pin with a scheduled GitHub workflow that opens a PR and cuts a patch tag.
2. Until then, bump the pin to 2.337.0 in a v1.3.4 patch. That removes the self-update each fresh install (and every ephemeral job) pays before its first job, which adds first-job latency and a second download.
3. Make doctor check the real version. Read the actual version on the host (readlink bin, or bin/Runner.Listener --version) and compare it with the latest upstream release and the 30-day window. Grep the journal for 'is deprecated and cannot receive messages' and detect a 0-byte bin.*/runsvc.sh (#4421, 203/EXEC). Record the actual version in state so upgrade-runner no longer "downgrades" the recorded pin.

A RunnerKit built on scaleset would still count as non-ARC, so nothing short of a GitHub policy change fixes this. (3) gh-aw. YES: `runs-on` accepts a string, an array or a runner-group object. It needs Linux with Docker on a unix socket, the runner user in the docker group, egress to api.githubcopilot.com, github.com and ghcr.io, and `runs-on-slim`, otherwise framework jobs run on hosted ubuntu-slim. RunnerKit today: likely works on Ubuntu x64, because setup_runner_image installs Docker and adds runnerkit-runner to the docker group. However, the Copilot CLI installer's default sudo steps go beyond RunnerKit's sudoers, which only allow the package managers, so `--rootless` is needed. gh-aw's own docs conflict on whether its AWF egress firewall needs sudo. (4) anthropics/claude-code-action. YES, and it is the best fit. It is a composite action that installs Bun 1.3.14, needs no Docker and documents no self-hosted requirements. Its optional bubblewrap step uses `sudo apt-get`, which RunnerKit allows. Missing: a separate HOME per job. Works on a personal repo, but only on a disposable host with passwordless sudo, setpriv and unprivileged user namespaces. Its default drop-sudo strategy is irreversible and its changes 'can outlive a job on reused self-hosted runners'. RunnerKit today: NO. action.yml runs `sudo chmod` and `sudo chown` unconditionally on Linux, which RunnerKit's sudoers does not allow. Separately, issue #160 shows drop-sudo breaking D-Bus and systemd-resolved, which would damage a persistent host. SCALESET: in the code, owner/repo maps to repository scope and the PAT is sent as a Bearer token to POST /repos/{o}/{r}/actions/runners/registration-token. The example registers into the default runner group (ID 1), so no org runner groups are needed. The ARC docs list a fine-grained PAT with 'Administration: Read and write' for repository runners, which is the credential RunnerKit already requests. **Implication:** Solo users can reach the 'agent-ready runners on hardware you own' repositioning for the Copilot cloud agent, gh-aw and claude-code-action on personal repos, because GitHub's docs gate none of them on an org or on ARC. It cannot promise Copilot code review, which is ARC-only by policy, and codex-action works only on disposable hosts. GitHub itself recommends single-use runners for agents, so the repositioning is only credible if RunnerKit gains a refilling ephemeral pool. Today's single-job `up --mode ephemeral` and persistent runners with a shared HOME are the wrong shape. Recommended sequence: (1) A 1–2 day spike on a user-owned repo with a fine-grained PAT that has Administration read/write. It should cover repo-level scale-set creation, registration of multiple labels including self-hosted/linux/x64 (to avoid breaking existing runs-on snippets), 3 parallel matrix jobs, and one Copilot cloud agent session with the firewall disabled. (2) If the spike passes, build a `--mode pool` on actions/scaleset, pinned to a commit and wrapped behind an internal interface because of the preview-API churn. Accept the Go 1.26.3 bump: measured cost is about half a day, with all tests green and three CI pins to change. Each job gets a fresh Hetzner VM or, on BYO, a fresh container or user. If the spike fails, build the same pool on the REST generate-jitconfig loop, which needs no Go bump and keeps the current labels. (3) Add an 'agent profile': an Ubuntu x64 gate, a unique single label for copilot-setup-steps, an nftables egress allowlist preloaded with the Copilot and Actions hosts (needed because Copilot's firewall must be off), a HOME reset per job, full sudo only inside disposable VMs (for codex-action drop-sudo), and doctor checks for these. (4) Update the docs/safety.md:125 non-goal. Day-2 reliability still matters: the scaleset listener has open stall and intermittent-failure bugs (#131, #105), so pool mode needs the same doctor/recover depth as today's runners.
