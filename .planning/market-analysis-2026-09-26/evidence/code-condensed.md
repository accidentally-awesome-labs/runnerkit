
# byo-bootstrap

The BYO path works like this: the laptop SSHes into the host and runs about seven bash scripts under a "scoped" passwordless-sudo list. The code is well instrumented, but the path is brittle. Several mechanics are solid: sudoers files are checked with visudo before an atomic move, runner tarballs are pinned and SHA-256 checked, the registration token travels in the script body rather than the laptop's command line and is redacted, a changed host key stops the run, and the Executor interface keeps things testable (bootstrap 81.8% coverage; all bootstrap, remote, preflight and install.sh tests pass). At HEAD, though, the documented path for the core audience is broken. That audience is Ubuntu home or desktop hosts where sudo needs a password. install.sh is now the only BYO sudoers installer, because byo-prepare was deleted in f017b2c. install.sh grants 15 fewer command paths than the Go template (tee, gpg, mkdir, unzip, usermod, dpkg, add-apt-repository, chmod, cp, cat, ln), so setup_runner_image fails exactly like the 2026-05-18 smoke Bug A. The v1.3.3 release notes also tell users to run `runnerkit byo-prepare`, which no longer exists. The allowlist is effectively full root: unrestricted su, tee, cp, install, dpkg, apt-get and systemctl mean `sudo su -` gives a root shell. The runner service user is also effectively root through the docker group, the optional apt-get CI sudo, and a service-user-owned svc.sh that lifecycle commands run with sudo. So the security story in code comments, docs and the curl|bash experiment is not accurate. The host key is pinned through a separate ssh-keyscan connection, while the real sessions run with StrictHostKeyChecking=no. The fingerprint shown to users is a hash of the whole keyscan line, so it cannot be checked against ssh-keygen output. setup_runner_image runs before create_runner_user, so on fresh hosts the service user is never added to the docker group and Rust is never installed, and a marker file then stops any retry. Real OS support is Ubuntu x64 only. Arch and openSUSE always exit 20; Fedora and RHEL are handed Ubuntu package names; arm64, Debian and Mint hit repos pinned to amd64 or to Ubuntu. Preflight still reports all of these as supported. Recovery from a failure mid-bootstrap is weak. Nothing runs host-side, there are no timeouts or keepalives, and caches and markers can block every later run (demonstrated). Failures are reported as 'Remote stderr (unknown)'. The highest-leverage fixes are small: one source of truth for sudoers with a CI diff, reordering the steps, wrapping remote errors, and verifying before extracting. The strategic fix is to replace the allowlist with a versioned, root-owned host helper that runs bootstrap as a transient systemd unit on the host.

# cli-ux

I built HEAD (64c3003) and ran it with an isolated state dir (RUNNERKIT_STATE_DIR plus env -i, with no GitHub or Hetzner credentials and no local ssh client). I exercised every subcommand's --help, the no-args wizard (non-TTY and a real PTY), --json on every read command, the error paths, and a synthetic two-repo state (BYO and cloud) to reach the list, status, doctor, logs, recover, down and destroy flows offline. The architecture is careful: dry-run plans before mutation, a typed exit-code enum, RKD error codes with docs URLs, redaction everywhere, and a cloud completion that names cleanup and billable IDs. The shipped binary undercuts that care in several places. (1) Unknown commands, unknown flags and bad flag values print nothing at all and just exit 1 or 2. That includes `runnerkit byo-prepare --host …`, which the v1.3.3 release notes tell users to run, and `register --extra-packages`. (2) The production prompter has no Input method, so every typed-confirmation flow is dead. Interactive `destroy` refuses in a real TTY, and so do the public-repo ack, the ephemeral-BYO ack, state replace and the BYO host prompt. Users are pushed to --yes, which skips confirmation entirely. (3) main.go never sets StateBaseDir. So `doctor --ignore` always fails, config.json is read from the current directory, and checklist sessions/ are written into whatever directory the user runs from. (4) `down`/`unregister` has no cloud guard, and its plan omits Hetzner resources: a cloud user can remove local state and orphan a billing VM. The JSON contract promised to agents is heterogeneous. doctor and status use different next_actions shapes under the same schema_version, error envelopes are stripped, and `redactions_applied` is always true. Health commands exit 0 even when doctor reports errors. The first-run wizard asks three questions but runs nothing, and tells the user to paste a workstation command "on" the SSH host. Time to first runner is good on cloud (smoke: ~3 min up). On BYO it is gated by prerequisites (gh or a fine-grained PAT, key-only SSH, a one-time curl|sudo install) and an unskippable install of Docker, browsers and language runtimes that users are never shown before they confirm. Most issues are cheap to fix. Fixing the silent-error, Input-prompter and state-dir bugs, plus a uniform JSON envelope, would remove most of the day-one frustration.

# cloud-ephemeral

Hetzner cloud provisioning in RunnerKit handles one persistent VM well: it gets consent before creating anything billable, saves partial resources as checkpoints, waits for readiness in several stages (cloud-init v3 now rejects `status: error`), and runs a verified, ordered destroy. The 2026-05-18 live smoke of the persistent path passed end to end in 498s. Ephemeral mode works differently from how the docs describe it. Each `up --mode ephemeral --cloud hetzner` creates exactly one VM and registers one `config.sh --ephemeral` runner with a normal registration token, not JIT. After that one job nothing re-registers, extra queued jobs wait until GitHub times them out, and the VM keeps billing until someone runs `runnerkit destroy` by hand. The TTL is not what the docs promise. The host timer is hardcoded to `OnActiveSec=24h` and ignores `--ephemeral-ttl`. It only stops the service and runs a finalizer; it never deletes the VM or deregisters the runner. The client-side `expires_at` does use the flag, but only for status labels. The job-completion finalizer runs as the unprivileged service user and cannot write its root-owned archive or state files; I reproduced this in a scratch simulation (exit 1). There is no autoscaling of any kind: no webhooks, no polling for queued jobs, no scale sets, no JIT. Each runner runs one job at a time, and state allows one runner per repo. The most serious finding, confirmed with a scratch test: `runnerkit down --yes` on a cloud runner returns ok and deletes local state, which is the only record of the Hetzner resource IDs, without touching Hetzner. The VM is orphaned and keeps billing. Other risks: no signal handling during provisioning, and no orphan sweep outside the smoke harness. The same laptop SSH key is uploaded to Hetzner on every provision, which Hetzner's fingerprint uniqueness rule should reject in common setups (inferred, not live-tested). The cost estimate is a fixed €4.90/month for every server type and region, while cpx22 now reportedly costs about €19.49/month after the June 2026 increase. Arm64 (CAX) is effectively broken: the image lookup ignores architecture and the image setup hardcodes amd64. The Provider interface is a sensible base, but Hetzner assumptions leak into the CLI, the state schema and cloud-init, and the SDK is still hcloud-go v1.59.2 (Nov 2024) while v2.49.0 is current.

# engineering-quality

Some things are good: dependency injection throughout, a clean acyclic package graph, a careful state store, a stable error-code registry, and cosign-signed releases. But reading the code and running targeted repros turned up several shipped defects that the suite cannot catch, because tests compare rendered bash strings against fake executors. None of them runs the generated shell. - The cloud-init "tolerate recoverable errors" fix can never run because `set -e` exits the script first (reproduced).
- The production binary never sets `StateBaseDir`, so `doctor --ignore` always fails, `doctor` breaks in any directory that has a non-RunnerKit `config.json`, and `up --host` writes `sessions/*.json` into the user's working directory (all reproduced).
- Package auto-detection, on by default, treats comment words and option arguments as apt package names (reproduced).

# github-state-security

RunnerKit gets its GitHub credential from `gh auth token` first and only falls back to `RUNNERKIT_GITHUB_TOKEN`. It works only with repo-scoped runners through five REST calls: repo metadata, registration token, removal token, list runners and delete runner. It has no org runners, runner groups, JIT config or GitHub App support. Its GitHub hygiene is better than average. The durable GitHub and Hetzner credentials stay on the workstation, only short-lived registration and removal tokens go to hosts over SSH stdin, state is secret-free by design (0600 file, atomic writes, secret-key denylist, backup before migration, refusal to touch newer schemas), and the public/fork gate runs before any side effect. The weaknesses sit where GitHub, the host and the job meet. (1) `upgrade-runner` sends an empty registration token after deleting the runner's credentials. A scratch test confirmed `RUNNERKIT_REGISTRATION_TOKEN=""`. (2) The registration token ends up in the argv of `sudo su -c` and `config.sh`, so it can appear in `ps` and in sudo's auth log. That contradicts both the code comment and PITFALLS.md. (3) The "scoped" sudoers allowlist is effectively root: it grants su, tee, cp, systemctl, apt-get and dpkg with any arguments. The runner user is in the docker group by default, and the runner-owned install directory holds a `svc.sh` that RunnerKit later runs as root. Any CI job on a persistent runner can therefore become root, and on multi-repo hosts it can take over the other repos' runners, because every repo shares the single `runnerkit-runner` user. (4) The state file has no locking. A scratch test running 20 concurrent `SaveRepository` calls kept only 1 repo, which can orphan billable cloud VMs. (5) The safety policy looks only at the visibility and fork bits, and only when `up` runs. A repo made public later keeps its persistent runner. A private fork is rejected with a "public repository" message, and `--allow-public-repo-risk` lets it through even though `EvaluateSafety` hard-codes forks as not allowed. Checking the security items in CONCERNS.md at HEAD: (a) SSH host-key checking is still turned off (system.go:218-219), and the problem is worse than described. ssh-keyscan and the real SSH session are separate connections, so pinning does not stop an active man-in-the-middle, and `logs` and `upgrade-runner` skip the fingerprint check entirely. (b) The HCLOUD_TOKEN value is now registered, but only in `up` and `destroy` (up.go:692, destroy.go:152). The GitHub token is registered only in the GitHub service's own private redactor. (c) The svc.sh wildcard is still there, and the CONCERNS line saying production is safe is wrong: the install directory is owned by the service user (install.go:240, script.go:53). (d) The package-name item still holds: the auto-detect notice is still hidden in JSON mode (up.go:2297). Signal handling is still missing (cmd/runnerkit/main.go:41-46). Shai-Hulud 2.0 worked by registering rogue self-hosted runners and planting discussion-triggered workflows, so the product has a clear opening for a runner and workflow audit feature built on its existing workflow-YAML scanner.

# ops-diagnostics

RunnerKit's day-2 layer (status, doctor, logs, recover, down, destroy, list, upgrade-runner) is carefully designed. It has a multi-source health classifier (local state, GitHub API, pinned SSH host key, systemd, labels, Hetzner), dry-run and typed confirmation for every mutating command, checkpointed partial cleanup, redaction everywhere, and a versioned JSON contract. The unit tests pass: ops 73.4% and cli 72.4% statement coverage, errcodes 100%. But the tests use fakes that always succeed, and the live smoke scripts never run `logs`, `recover` or `upgrade-runner`. Several serious runtime bugs survive because of that; I reproduced each in the built binary or in throwaway tests in a scratch copy of the repo. (1) `upgrade-runner`, which `doctor --fix` also calls, re-runs configure with an EMPTY registration token after `rm -f .runner .credentials`. It also uses `tar --skip-old-files`, so the old runner binaries are never replaced. (2) `logs` and the doctor OOM heuristics call journalctl with the saved unit name, which is not the real `actions.runner.<owner-repo>.<name>.service` unit, so they get no entries. On cloud hosts the SSH user also has no journal read access. (3) The production binary never sets StateBaseDir. As a result `doctor` reads config.json from the current directory, `--ignore` always fails, and a malformed config.json in a project breaks doctor. (4) `down` deletes local state and reports ok when removing the runner files failed. (5) `down`/`destroy` against a dead host can never clear state, and they exit 0 on partial cleanup. When GitHub auth or SSH fails, doctor also reports false positives: offline, label drift, install path missing, stage "uninstalled", and it recommends a destructive `--reregister`. There is no continuous monitoring, alerting, metrics, job-level visibility, disk/docker hygiene or workspace cleanup. Everything is pulled on demand from the laptop, runs sequentially over separate SSH connections, and exit codes do not reflect health. The errcodes registry is well structured, but 19 of 51 codes have no production emit site, and doctor never prints the RKD IDs the docs tell users to look up. For a user with 5 repos on 2 hosts, day-2 means running per-repo commands by hand, getting generic "required facts are missing" summaries, and finding out a runner is down only when jobs queue.

# product-history-traction

RunnerKit set out to get a solo developer's GitHub Actions self-hosted runner online in about 10 minutes, on a BYO Linux box over SSH or on a Hetzner VM (.planning/PROJECT.md:5-11). It shipped a lot of that in a single 21-day sprint: 265 commits from one author between 2026-04-28 and 2026-05-18, 6 phases and 35 plans, 18 tags (v1.0.0 to v1.3.3), with at least 88 commits carrying Cursor or Claude co-author trailers. Measured time to a working runner beat the target (BYO 126-149s, cloud 167-287s), and the cloud path was green end-to-end on 2026-05-18. The BYO privilege model was the recurring failure: 23 of the 37 fix commits (62%) touched bootstrap, preflight or sudo code, 34 numbered bugs were logged, and Phase 6 needed 21 live-smoke attempts, with 11 of its 16 plans being gap closures. Each fix widened the scoped NOPASSWD allowlist, which now includes unrestricted su, cp, cat, tee and chmod. The bug class came back after v1 (v1.3.1 broke BYO; found 5 days later). v1.3.3's fix did not reach the one documented BYO install path: install.sh still carries the old 17-command allowlist, and the release notes tell users to run `byo-prepare`, a command removed in v1.0.8. Several things were deferred and never started: the v1.4.0 install.sh pivot with path-scoped sudoers, SEED-003 (Claude plugin), SEED-004 tier 2, the cost controls COST-01..03, and the project config loader. The original research called market demand low-to-medium confidence and said to "validate with early users", but no validation, launch or pricing analysis appears anywhere in the repo. Traction is effectively zero: the public repo has 0 stars, 0 forks, 0 watchers, 0 issues and 0 PRs ever, 35 total downloads across 16 releases (16 of them darwin_arm64, consistent with the maintainer's own Mac), no LICENSE, and no commits for 130 days. # workload-compatibility

I checked how close a RunnerKit runner comes to a GitHub-hosted runner for real CI jobs. RunnerKit has put real effort into matching the hosted image: about 75 apt packages plus Node, Go, Rust, Java, .NET, Docker, browsers and gh. On the one tested combination (Hetzner cpx22, Ubuntu 24.04, x64) a runner comes online in roughly 6-7.5 minutes. The cloud smoke took 498s, and that figure includes status, doctor and destroy.

The claim of GitHub-hosted parity does not hold, and several failures happen before a job does anything. The bootstrap runs `setup_runner_image` before it creates the runner user, so on every fresh host the runner user is never added to the `docker` group and Rust is never installed. Both failures are silent, and the version marker then stops any later run from repairing them. As a result, `docker build`, `services:` and `container:` jobs fail out of the box. Cloud runners also give the job user no sudo at all, so the very common `sudo apt-get install` step fails.

The image script hard-codes amd64 in six places, so arm64 hosts cannot finish bootstrap even though preflight and the docs say arm64 is supported. Hosts outside the Debian family are sent Debian package names through dnf and fail. Each repo gets exactly one fixed-name runner, so matrix builds run one leg at a time. Ephemeral mode means one job per manual `runnerkit up`. Nothing cleans persistent workspaces or prunes Docker. macOS, Windows, GPU, Android emulator and iOS are not supported, and the docs wrongly present macOS as an "advanced BYO" option.

`upgrade-runner` deletes the runner's credentials and then re-runs `config.sh` with an empty registration token. The runner is left unconfigured and will not come back after its next restart.

No smoke test ever sends a workflow job to the runner; the smokes only check that it is online and idle. That is why these workload failures went unnoticed while the lifecycle tests stayed green. The most valuable next steps are cheap:
- create the runner user before image setup, bump the image version so existing hosts re-run it, and check `docker info` as the runner user;
- give cloud runners sudo that matches hosted runners, and add swap;
- make image setup architecture-aware;
- add a canary workflow to the smoke tests;
- add runner-count and custom-label flags so matrix legs can run in parallel.

## Features
- [solid] Native build toolchain on Ubuntu x64 (baseline apt set): ~75 apt packages mirroring actions/runner-images (build-essential, gcc/g++, pkg-config, libssl-dev, xvfb, jq, rsync, shellcheck, etc.). Installed via cloud-init on Hetzner and via fix_dependencies on BYO.
- [partial] Preinstalled language runtimes (Node, Python pip/venv, Go, Rust, Java 17, .NET 8): Installed by the setup_runner_image step on Ubuntu/Debian/Mint so workflows that assume tools are on PATH (as on ubuntu-latest) work without setup-* actions.
- [partial] setup-* actions and the runner tool cache: actions/setup-node/go/java/python/dotnet download into the runner's default RUNNER_TOOL_CACHE (<work>/_tool). The work dir is /var/lib/runnerkit/work/<runner>.
- [solid] actions/cache and artifacts: Uses GitHub's cache/artifact service over HTTPS, same as hosted. zstd is installed so compression matches hosted runners.
- [fragile] Docker builds (docker build, buildx, compose, Docker-in-Docker): Docker CE plus the buildx and compose plugins are installed, and the runner user is supposed to join the docker group. A persistent host keeps the layer cache warm.
- [fragile] Service containers (`services:`) and container jobs (`container:`): These need Linux, Docker, and a runner user that can reach /var/run/docker.sock.
- [stub-or-missing] Matrix builds and concurrency: One runner process per repo means one job at a time per repo. The runner name is fixed (`runnerkit-owner-repo-local`) and registered with --replace. There is no --labels, --count or pool flag.
- [stub-or-missing] arm64 hosts (Graviton/Ampere/Pi/Hetzner CAX): Preflight accepts arm64 and an arm64 runner tarball is pinned, but image setup is amd64-only and cloud arm64 is not planned.
- [stub-or-missing] macOS and Windows runners: Not supported. The Windows gap is documented honestly; the macOS claim in docs is wrong.
- [stub-or-missing] GPU workloads: No GPU detection, NVIDIA driver or container-toolkit setup, or custom 'gpu' label. Hetzner Cloud has no GPU server types in this path.
- [partial] Browser/E2E testing (Playwright, Cypress, Selenium): Chrome, matching ChromeDriver, Firefox, Geckodriver and xvfb are installed on Ubuntu x64.
- [stub-or-missing] Mobile (Android/iOS) builds: Java 17 is present, but there is no Android SDK or ANDROID_HOME and no KVM access for emulators. iOS needs macOS, which is unsupported.
- [fragile] Jobs that use sudo (sudo apt-get, sudo tee, etc.): Hosted runners have passwordless sudo. BYO can opt into package-manager-only sudo through install.sh with RUNNERKIT_GRANT_CI_SUDO=1. Cloud runners get no runner-user sudo at all.
- [stub-or-missing] Persistent workspace hygiene, disk and large monorepos: Nothing cleans up between jobs: no Docker prune, no job hooks, no disk-usage monitoring beyond a 2 GiB floor, and no volumes on cloud.
- [partial] Runner version management and auto-update: The runner's own self-update is left on (no --disableupdate), and doctor flags stale pins. The `upgrade-runner` command itself is broken.
- [fragile] Ephemeral mode for untrusted/public workloads: Registers a single-job runner with a 24h TTL. After one job the runner is finished; there is no re-registration loop, and the cloud VM keeps billing until destroy.
- [partial] Security isolation of persistent and multi-repo runners: Non-root runner user, a public-repo gate with typed acknowledgement, and repo-scoped labels. However, all repos on a host share one UID, and the 'scoped' sudo grants are effectively root.
- [fragile] Auto-detection of apt packages from workflow YAML: Scans .github/workflows in the current directory with a regex and merges the matches into apt installs on both the BYO and cloud paths.
- [fragile] Non-Ubuntu Linux hosts (Fedora/RHEL/Rocky/Alma/Arch/openSUSE, Debian, Mint): Preflight 'recognizes' 11 distros, but only Ubuntu is actually provisioned correctly.
- [partial] First-run time vs the ~10-minute promise: Measured only on cloud: 498s end to end on cpx22 (up, status, doctor x3, list, destroy), so `up` itself is about 6-7.5 minutes. No BYO timing exists since image setup landed.
